# Engine Comparison

Ferroni next to seven other engines on two Blacksmith runner profiles:
C Oniguruma, Ruby's Onigmo, PCRE2 with and without JIT, fancy-regex in
three configurations (default, seek mode and RegexSet), Rust's `regex`
crate and, for highlighting, Shiki's JavaScript engine.

This full run measures **85 cases per host** on the merged runtime commit
`d791bf1b011f6e98619969872a4d7cb7161912a7`. All sixteen builds (the original full run and its repeat) used that exact commit in clean
checkouts. Their build receipts, input hashes and toolchains are retained in
[the full-run data](https://github.com/sebastian-software/ferroni/tree/main/benches/results/blacksmith-2026-10-13-38439201637)
and [full repeat](https://github.com/sebastian-software/ferroni/tree/main/benches/results/blacksmith-2026-10-13-38442515829).
The full suite was repeated after large x86 control shifts in the first
run. Its complete case set replaces the original run on both hosts;
both runs remain available.

## How to read the numbers

Each table cell shows **Apple Silicon above x86-64**. Ferroni's column is
the Criterion mean; other columns divide that engine's time by Ferroni's.
**Above 1.00, Ferroni is faster; below 1.00, the other engine is faster.**
The summary uses equally weighted geometric means across accepted tasks and
both hosts. Coverage differs between engines, so a mean over fewer compatible
cases does not establish a ranking over the complete workload.

Every engine must first reproduce the reference matches and capture bounds,
or the recorded scanner results. Rejected patterns and different answers get
`n/a`, with reasons below. A dash means the engine has no variant for that API
or syntax. Compilation and preparation have separate rows and stay outside
execution timings. These are point estimates from one full run; differences
within about 10% should not be read as a ranking.

The workflow requests five seconds, 30 samples and 500 ms warmup. The existing
`battle_bench` groups override measurement time to four seconds; the captured
scanner replays use five seconds. Shiki JS warms up for one second and uses its existing Node batch timer.
Within each case-set job, engines run consecutively on the same VM for each
case; they do not compete in parallel. The four case sets use separate VMs per host profile.
The raw estimates, individual 95% confidence intervals and logs remain in the
run data. Those intervals describe samples within a job and do not include
between-run VM variation. Physical placement and scheduling are uncontrolled.

PCRE2 JIT is 2.0× faster than Ferroni across 31/32 everyday tasks and
3.1× faster across 16/17 advanced tasks.
For the three portable whole-document scanner replays,
Ferroni is 9.9× faster than PCRE2 JIT.
Those replays compare Ferroni's multi-pattern scanner with PCRE2's
pattern-by-pattern adapter; they do not imply the same result for a single regex.

## Highlighting

Replays run recorded scanner calls with their original pattern priority and
captures. C, Java, PHP, C++ and SCSS come from Shiki's Oniguruma engine;
JSON and Astro come from Ferriki's tokenizer. The per-corpus READMEs retain
capture provenance and workload boundaries.

Ferroni and C use the Oniguruma RegSet scanner API; Ferroni can narrow the
candidate positions with the conservative DFA pre-filter in
[ADR-008](/adr/008-rust-only-optimizations). PCRE2 and Onigmo search pattern
by pattern. fancy-regex's RegexSet is a separate configuration built once per
scanner, while its default and seek modes also search pattern by pattern.
Shiki JS is `@shikijs/engine-javascript` 4.5.0, timed in Node over 1 ms batches.
Scanner compilation and fixture loading remain outside timing. The Node replay
creates fresh engine strings inside its loop; the Rust replay prepares its
strings outside the timed closure. These adapter boundaries are retained in the
harnesses and should be considered when interpreting their ratios.

Shiki's **Oniguruma WASM engine is not timed** in this comparison. It was used
to capture the C, Java, PHP, C++ and SCSS reference traces. The Oniguruma (C)
column times the native vscode-oniguruma scanner adapter; it does not stand in
for a Shiki WASM measurement. Shiki JS means the JavaScript regex engine and
its scanner adapter in Node, not the whole Shiki highlighter. All replay rows
exclude the TextMate tokenizer, theme processing and HTML rendering.

Ferroni's pre-filter was inspired by Keith Hall's
[seek-filter proposal](https://github.com/fancy-regex/fancy-regex/issues/101#issuecomment-3146668829)
and [fancy-regex implementation](https://github.com/fancy-regex/fancy-regex/pull/246).
The replays describe these adapters and workloads, rather than a universal
speed claim about the underlying engines.

## CSS and the October 9 baseline

| Host             | Oct 9, µs | Before CSS PR, µs | Current, µs | Current vs. before | C-relative vs. before |
| ---------------- | --------- | ----------------- | ----------- | ------------------ | --------------------- |
| M4 Pro (virtual) | 72.62     | 73.81             | 76.44       | -3.56%             | +3.42%                |
| Linux x86-64     | 75.54     | 78.94             | 97.54       | -23.57%            | -5.65%                |

Positive percentages mean less execution time. The C-relative companion is
`100 × (1 - (new_Ferroni / new_C) / (old_Ferroni / old_C))`; it is a diagnostic
for changes shared with the reference engine, not a causal correction.
The current full run and its repeat used the expected current main SHA, with unchanged fixtures
and harnesses. Their VM scheduling and physical hosts can still differ. The first full run's
x86 shared job reported an Intel Xeon without AVX-512, unlike the preceding
AMD EPYC jobs. The same runner label therefore does not guarantee the same CPU.
The receipts retain the processor and feature flags for every case set.

The local same-host investigation on an M1 Ultra did not reproduce a material
October 9 regression: 102.409 → 101.873 µs (+0.52%). The CSS PR's paired local
native comparison saved 5.33%; independent fixed-work lanes saved 4.76% for one
copy and 5.19% for four. Those local results do not establish the same gain on a
virtual M4. [PR #357](https://github.com/sebastian-software/ferroni/pull/357)
retains the complete measurement description and controls.

The historical comparison uses full run
[37989957431](https://github.com/sebastian-software/ferroni/actions/runs/37989957431)
for text processing and micro cases, and the later
[37999607702](https://github.com/sebastian-software/ferroni/actions/runs/37999607702)
for highlighting. The earlier CSS result predates pre-filter retirement and
would overstate the accumulated gain. The full-run report retains all 162 matched
historical comparisons; JSON and Astro are excluded from those averages.

## Cases an engine cannot run

Both hosts report the same compatibility exclusions. Every raw message is
retained in `engine-notes.json` next to its measurements.

| `unicode_case_folding`        | `regex`, PCRE2, PCRE2 JIT, fancy-regex | Simple case folding only: `straße` does not match `STRASSE`                                                     |
| `emoji_graphemes`             | fancy-regex                            | No `\X` grapheme clusters                                                                                       |
| `variable_lookbehind`         | Onigmo                                 | Rejects the lookbehind of variable length (error -122)                                                          |
| `absent_comments`             | PCRE2, PCRE2 JIT                       | No absent operator `(?~...)`                                                                                    |
| `subexp_call_balanced`        | fancy-regex, fancy-regex (seek)        | After the recursive call, group 1 holds the innermost match (`17..21`); Oniguruma keeps the outermost (`4..21`) |

| `conditional_brackets`        | fancy-regex (seek)                     | Seek mode requires the conditional's then-branch even where its group is unset, so it skips the second match    |
| C++ replay                    | PCRE2, PCRE2 JIT                       | The stacked quantifier `\s+{0,1}` is a syntax error                                                             |
| C++ replay                    | Onigmo                                 | `\s+{1,0}`, a possessive repeat in Oniguruma, is an error (-202); several lookbehinds are rejected (-122)       |
| SCSS replay                   | PCRE2, PCRE2 JIT                       | `\h` and nested classes such as `[a-z[^\x00-\x7F]]` read differently, so some calls match another pattern       |

| Astro document and scanner 22 | fancy-regex (all configurations)       | Reports an empty match where the recorded result is no match                                                    |

zero-length captures, so only those explicitly recorded differences count as
equivalent. The validation notes retain their counts.

## Reproducing

```bash
git checkout d791bf1b011f6e98619969872a4d7cb7161912a7
./scripts/prepare-oniguruma-sources.sh
./scripts/prepare-onigmo-sources.sh
pnpm install --frozen-lockfile --dir benches/shiki_js
./scripts/compare-engines.py run /tmp/ferroni-compare --cases shared oniguruma micro textmate --measure-seconds 5
./scripts/compare-engines.py report /tmp/ferroni-compare.md /tmp/ferroni-compare
```

Or dispatch `blacksmith-comparison.yml` with `--ref main`, `platform=both`,
`cases=all` and `measure_seconds=5`. Verify the returned run's head SHA and every
build receipt before publishing it. Tables are generated with
`./scripts/compare-engines.py tables benches/results/blacksmith-2026-10-13-38439201637 benches/results/blacksmith-2026-10-13-38442515829`;
homepage figures with `./scripts/compare-engines.py figures benches/results/blacksmith-2026-10-13-38439201637 benches/results/blacksmith-2026-10-13-38442515829 docs/app/data/engine-comparison.json`.

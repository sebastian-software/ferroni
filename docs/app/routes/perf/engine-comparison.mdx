# Engine Comparison

Ferroni next to seven other engines on two cloud hosts: C Oniguruma, Ruby's
Onigmo, PCRE2 with and without JIT, fancy-regex, Rust's `regex` crate and, for
highlighting, Shiki's JavaScript engine. The focus is everyday regular
expressions on realistic text; highlighting counts only grammars every engine
can run. The run comes from the manually dispatched
[Blacksmith comparison](https://github.com/sebastian-software/ferroni/actions/workflows/blacksmith-comparison.yml)
workflow, so anyone can repeat it on the same runner types.

Every engine first has to reproduce Oniguruma's matches and capture bounds for
a case, or every captured Shiki result for a highlighting replay. Only then is
it timed. Where an engine rejects a pattern or answers differently, the table
says `n/a` and [the reason is listed](#cases-an-engine-cannot-run). A dash means
the engine has no variant for that case: the `regex` crate lacks the syntax, or
the case uses an API (Oniguruma's RegSet, the grammar loader) the engine does
not have.

## How to read the tables

Each cell holds the **Apple Silicon** value on top and the **x86-64** value
below it. The Ferroni column is the Criterion mean. Every other column is that
engine's time divided by Ferroni's, the same convention as "C / Ferroni" on the
other pages: **above 1.00, Ferroni is faster**; below 1.00, the other engine is.

These are point estimates from one run with 30 samples over 3 seconds per case
and engine. Differences within about 10% are not a ranking. The raw estimates,
confidence intervals and logs are kept with the
[run data](https://github.com/sebastian-software/ferroni/tree/main/benches/results/blacksmith-2026-10-01-36926978824).

## Text processing

Each task collects every match with its captures over one generated document,
or checks a batch of inputs
([`benches/regex_tasks.rs`](https://github.com/sebastian-software/ferroni/blob/main/benches/regex_tasks.rs),
[`benches/general_regex.rs`](https://github.com/sebastian-software/ferroni/blob/main/benches/general_regex.rs)):
an HTML page of 88 KB, a server log of 74 KB, a chat log with emoji of 27 KB,
Markdown of 55 KB, JSON of 53 KB, CSV of 30 KB and JavaScript-like source of
58 KB. The patterns range from tags, emails and timestamps to whole-grammar
expressions: the RFC 5322 address syntax, every IPv6 notation, RFC 3986 URLs
and a 200-word alternation.

### Shared syntax

of 32 tasks, by up to 36x on email extraction; C is faster on the RFC 5322 and
IPv6 expressions. Against Onigmo it is ahead in 29 tasks, and the PCRE2 interpreter is mixed. PCRE2's JIT is faster than Ferroni in 27 tasks and the
`regex` crate in 23. The automaton-based engines, `regex` and fancy-regex (which hands these patterns to `regex`), run the RFC 5322 and IPv6 expressions 14x to 33x faster than Ferroni and 2x to 7x faster than PCRE2's JIT. Only Oniguruma, Ferroni and Onigmo apply
full Unicode case folding, so only they find `STRASSE` for `straße`.

### Oniguruma syntax

Element pairs through backreferences, possessive and atomic groups, lookbehind,
quoted strings with either quote, grapheme clusters, password rules with four
lookaheads, recursion through `\g<0>`, the absent operator and conditionals.
Ferroni is faster than C Oniguruma in 14 of 17 tasks; in the others C is up to 30% faster on one host. PCRE2's JIT is faster than Ferroni in every task it can run.
fancy-regex runs all but two in its Oniguruma mode, 1.3x to 16x slower than Ferroni except on the password rules, where it is twice as fast.

## Highlighting

The highlighting replays play back the scanner calls Shiki makes for a whole
document, recorded from Shiki's Oniguruma (WASM) engine with
[`benches/shiki_js/capture.mjs`](https://github.com/sebastian-software/ferroni/blob/main/benches/shiki_js/capture.mjs).
Each document is the TIOBE "Orders" program repeated 16 times, about 14 to 18 KB.
Ferroni and C use Oniguruma's RegSet scanner (C through the scanner wrapper of
vscode-oniguruma). Onigmo, PCRE2 and fancy-regex have no RegSet and search
pattern by pattern, which is what vscode-oniguruma itself does on lines of
1,000 bytes or more. Shiki JS is `@shikijs/engine-javascript` 4.5.0 with its
defaults, timed in Node over 1 ms batches rather than with Criterion.

These engines were not built for highlighting, which puts many patterns in one
search. The replays show what that costs when an application uses them for it.

### Portable grammars

C, Java and PHP use no syntax another engine rejects or reads differently;
every engine reproduces every captured result. Ferroni is 2.7x to 5.7x faster than C Oniguruma and 1.3x to 5.8x faster than PCRE2's JIT here. Shiki's JavaScript engine comes closest: on the PHP document it is faster than Ferroni on Apple Silicon and as fast on x86-64; on the others it is 2x to 3.4x slower.

### Grammars with Oniguruma-only syntax

TextMate grammars are written for Oniguruma, and many use its particular
syntax. The C++ grammar writes quantifiers such as `\s+{0,1}` that PCRE2
rejects and that Onigmo rejects as `\s+{1,0}`. The SCSS grammar uses `\h`,
a hex digit in Oniguruma and a horizontal space in PCRE2. A scan of all 260
Shiki grammars finds these constructs in most large ones. These replays show
what highlighting with such grammars costs in the engines that run them.

## Cases an engine cannot run

Both hosts report exactly the same cases. The raw messages are in the run data.

| Case                   | Engines                                | Why                                                                                                             |
| ---------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `unicode_case_folding` | `regex`, PCRE2, PCRE2 JIT, fancy-regex | Simple case folding only: `straße` does not match `STRASSE`                                                     |
| `emoji_graphemes`      | fancy-regex                            | No `\X` grapheme clusters                                                                                       |
| `variable_lookbehind`  | Onigmo                                 | Rejects the lookbehind of variable length (error -122)                                                          |
| `absent_comments`      | PCRE2, PCRE2 JIT                       | No absent operator `(?~...)`                                                                                    |
| `subexp_call_balanced` | fancy-regex                            | After the recursive call, group 1 holds the innermost match (`17..21`); Oniguruma keeps the outermost (`4..21`) |
| C++ replay             | PCRE2, PCRE2 JIT                       | The stacked quantifier `\s+{0,1}` is a syntax error                                                             |
| C++ replay             | Onigmo                                 | `\s+{1,0}`, a possessive repeat in Oniguruma, is an error (-202); several lookbehinds are rejected (-122)       |
| SCSS replay            | PCRE2, PCRE2 JIT                       | `\h` and nested classes such as `[a-z[^\x00-\x7F]]` read differently, so some calls match another pattern       |

Shiki JS reports 96 C++ calls and 16 Java calls with an empty capture group as
unset or the reverse. vscode-textmate skips zero-length captures, so those
calls count as equal; no other engine needs this.

# Engine Comparison

Ferroni next to seven other engines on two cloud hosts: C Oniguruma, Ruby's
Onigmo, PCRE2 with and without JIT, fancy-regex in three configurations (its
default, seek mode and RegexSet), Rust's `regex` crate and, for highlighting,
Shiki's JavaScript engine. The focus is everyday regular
expressions on realistic text; highlighting counts only grammars every engine
can run. The run comes from the manually dispatched
[Blacksmith comparison](https://github.com/sebastian-software/ferroni/actions/workflows/blacksmith-comparison.yml)
workflow, so anyone can repeat it on the same runner types.

Every engine first has to reproduce Oniguruma's matches and capture bounds for
a case, or every captured Shiki result for a highlighting replay. Only then is
it timed. Where an engine rejects a pattern or answers differently, the table
says `n/a` and [the reason is listed](#cases-an-engine-cannot-run). A dash means
the engine has no variant for that case: the `regex` crate lacks the syntax, or
the case uses an API (Oniguruma's RegSet, the grammar loader) the engine does
not have.

## How to read the tables

Each cell holds the **Apple Silicon** value on top and the **x86-64** value
below it. The Ferroni column is the Criterion mean. Every other column is that
engine's time divided by Ferroni's, the same convention as "C / Ferroni" on the
other pages: **above 1.00, Ferroni is faster**; below 1.00, the other engine is.

These are point estimates from one run with 30 samples over 3 seconds per case
and engine. Differences within about 10% are not a ranking. The raw estimates,
confidence intervals and logs are kept with the run data
([text processing and short searches](https://github.com/sebastian-software/ferroni/tree/main/benches/results/blacksmith-2026-10-09-37989957431),
[highlighting](https://github.com/sebastian-software/ferroni/tree/main/benches/results/blacksmith-2026-10-09-37999607702));
[Measurement context](#measurement-context) says why there are two runs.

## Text processing

Each task collects every match with its captures over one generated document,
or checks a batch of inputs
([`benches/regex_tasks.rs`](https://github.com/sebastian-software/ferroni/blob/main/benches/regex_tasks.rs),
[`benches/general_regex.rs`](https://github.com/sebastian-software/ferroni/blob/main/benches/general_regex.rs)):
an HTML page of 88 KB, a server log of 74 KB, a chat log with emoji of 27 KB,
Markdown of 55 KB, JSON of 53 KB, CSV of 30 KB and JavaScript-like source of
58 KB. The patterns range from tags, emails and timestamps to whole-grammar
expressions: the RFC 5322 address syntax, every IPv6 notation, RFC 3986 URLs
and a 200-word alternation. These tables and the short searches are within
noise of the previous publication (run 37782529019, before the pre-filter,
which touches only the scanner): every engine's geometric mean moved by less
than 10%, except Onigmo on the ten-branch alternation of the short searches,
and the counts below by one or two tasks.

### Shared syntax

Patterns the `regex` crate also runs. Ferroni is faster than C Oniguruma in 28
of 32 tasks, by up to 33x on email extraction; C is faster on the RFC 5322 and
IPv6 expressions, and two tasks are split between the hosts. Against Onigmo it
is ahead in 30 tasks, and the PCRE2 interpreter is mixed. PCRE2's JIT is faster
than Ferroni in 27 tasks and the `regex` crate in 23. The automaton-based
engines, `regex` and fancy-regex (which hands most of these patterns to
`regex`), run the RFC 5322 and IPv6 expressions 14x to 31x faster than Ferroni
and 1.7x to 6.5x faster than PCRE2's JIT. fancy-regex's seek mode changes only
the patterns it runs in its own backtracking engine, and closes most of their
gap: hex colors go from 51x to 63x slower than Ferroni to 2.7x,
case-insensitive keywords from 26x to 39x slower to 0.9x to 1.3x, URLs from 19x
to 40x slower to 0.9x to 1.1x. Only Oniguruma, Ferroni and Onigmo apply full
Unicode case folding, so only they find `STRASSE` for `straße`.

### Oniguruma syntax

Element pairs through backreferences, possessive and atomic groups, lookbehind,
quoted strings with either quote, grapheme clusters, password rules with four
lookaheads, recursion through `\g<0>`, the absent operator and conditionals.
Ferroni is faster than C Oniguruma in 12 of 17 tasks; the other five are split
between the hosts, with C up to 1.3x faster on one of them. PCRE2's JIT is
faster than Ferroni in every task it can run. fancy-regex runs all but two in
its Oniguruma mode, 1.5x to 15x slower than Ferroni except on the password
rules, where it is 1.8x faster. Its seek mode answers two more tasks
differently (the conditional and the recursive JSON object, listed
[below](#cases-an-engine-cannot-run)). On the 13 it runs it is faster than the
default in ten and faster than Ferroni in three, but it takes about 1,600x
Ferroni's time on the recursive div pattern, whose many matches in one document
make each seek search scan to the end of the input, and 15x to 17x on the
absent expression.

## Highlighting

The highlighting replays play back the scanner calls Shiki makes for a whole
document, recorded from Shiki's Oniguruma (WASM) engine with
[`benches/shiki_js/capture.mjs`](https://github.com/sebastian-software/ferroni/blob/main/benches/shiki_js/capture.mjs).
Each document is the TIOBE "Orders" program repeated 16 times, about 14 to 18 KB.
Ferroni and C use Oniguruma's RegSet scanner (C through the scanner wrapper of
vscode-oniguruma); Ferroni's scanner first narrows each search with the DFA
pre-filter of [ADR-008](/adr/008-rust-only-optimizations), which decides before
any attempt which patterns can match where. Onigmo and PCRE2 have no RegSet and
search pattern by pattern, which is what vscode-oniguruma itself does on lines
of 1,000 bytes or more. fancy-regex has a `RegexSet`, which the replays run as its own
configuration: one set per scanner, built once, returning the earliest match
and, among the patterns that start there, the lowest pattern index with its
captures. The other two fancy-regex configurations search pattern by pattern:
the default, and seek mode, which enables fancy-regex's seek pre-filter for
backtracking patterns (off by default). Shiki JS is
`@shikijs/engine-javascript` 4.5.0 with its defaults, timed in Node over 1 ms
batches rather than with Criterion.

These engines were not built for highlighting, which puts many patterns in one
search. The replays show what that costs when an application uses them for it.

Ferroni's lead here is new. Before the pre-filter, in
[run 37839952403](https://github.com/sebastian-software/ferroni/actions/runs/37839952403)
on the branch of [#316](https://github.com/sebastian-software/ferroni/pull/316)
(the last comparison without it; its x86-64 runner was an Intel Xeon),
fancy-regex's `RegexSet` was faster than Ferroni on the geometric mean of the
ten replays, 1.5x on Apple Silicon and 1.6x on x86-64, while C Oniguruma and
Shiki JS were 5.1x and 2.4x slower than Ferroni. With the pre-filter, Ferroni
is 1.9x faster than the `RegexSet` on the same mean (2.0x on Apple Silicon,
1.8x on x86-64; from parity on the Java scanner group to 3.8x on the C++
document), 15x faster than C Oniguruma (8.5x to 33x) and 7.3x faster than
Shiki JS (2.7x to 15x).

### Portable grammars

C, Java and PHP use no syntax another engine rejects or reads differently;
every engine reproduces every captured result. Ferroni is 8.5x to 20x faster
than C Oniguruma and 4.9x to 19x faster than PCRE2's JIT here. fancy-regex's
`RegexSet` comes closest: on the Java replays and the PHP document it is within
1.0x to 1.3x of Ferroni, on the C replays and the PHP scanner group 2.0x to
3.7x behind. Its other two configurations search pattern by pattern and are
10x to 28x (seek mode) and 51x to 382x (default) slower. Shiki's JavaScript
engine is 2.9x to 12x slower.

### Grammars with Oniguruma-only syntax

TextMate grammars are written for Oniguruma, and many use its particular
syntax. The C++ grammar writes quantifiers such as `\s+{0,1}` that PCRE2
rejects and that Onigmo rejects as `\s+{1,0}`. The SCSS grammar uses `\h`,
a hex digit in Oniguruma and a horizontal space in PCRE2. A scan of all 260
Shiki grammars finds these constructs in most large ones. These replays show
what highlighting with such grammars costs in the engines that run them:
Ferroni is 9.8x to 33x faster than C Oniguruma, 16x to 19x faster than Onigmo
on SCSS and 1.4x to 3.8x faster than fancy-regex's `RegexSet`; Shiki JS is 2.7x
to 15x slower.

### Grammar scanners

The complete Shiki grammars for TypeScript, CSS and Rust: compiling a grammar,
re-scanning one line, and tokenizing a document line by line. Only Ferroni and
C Oniguruma have a grammar loader and a RegSet scanner here. Ferroni scans 16x
to 74x faster. C compiles the TypeScript and Rust grammars 1.2x to 2.8x faster,
Ferroni the CSS grammar 1.1x to 1.5x faster; part of Ferroni's compile time now
goes into the seek each scanner pattern derives for the pre-filter. The flat
CSS scanner, 117 patterns in one set, is a set on which the pre-filter retires
itself within its first pass (ADR-008); the earlier run of the same day, before
[#324](https://github.com/sebastian-software/ferroni/pull/324) taught it to,
had its scan rows at 11 to 16 ms.

## Cases an engine cannot run

Both hosts report exactly the same cases. The raw messages are in the run data.

| Case                     | Engines                                | Why                                                                                                             |
| ------------------------ | -------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `unicode_case_folding`   | `regex`, PCRE2, PCRE2 JIT, fancy-regex | Simple case folding only: `straße` does not match `STRASSE`                                                     |
| `emoji_graphemes`        | fancy-regex                            | No `\X` grapheme clusters                                                                                       |
| `variable_lookbehind`    | Onigmo                                 | Rejects the lookbehind of variable length (error -122)                                                          |
| `absent_comments`        | PCRE2, PCRE2 JIT                       | No absent operator `(?~...)`                                                                                    |
| `subexp_call_balanced`   | fancy-regex, fancy-regex (seek)        | After the recursive call, group 1 holds the innermost match (`17..21`); Oniguruma keeps the outermost (`4..21`) |
| `json_objects_recursive` | fancy-regex (seek)                     | Seek mode skips the outer `\g<0>` match and reports the inner object (`136..152` instead of `4..208`)           |
| `conditional_brackets`   | fancy-regex (seek)                     | Seek mode requires the conditional's then-branch even where its group is unset, so it skips the second match    |
| C++ replay               | PCRE2, PCRE2 JIT                       | The stacked quantifier `\s+{0,1}` is a syntax error                                                             |
| C++ replay               | Onigmo                                 | `\s+{1,0}`, a possessive repeat in Oniguruma, is an error (-202); several lookbehinds are rejected (-122)       |
| SCSS replay              | PCRE2, PCRE2 JIT                       | `\h` and nested classes such as `[a-z[^\x00-\x7F]]` read differently, so some calls match another pattern       |

Shiki JS reports 96 C++ calls and 16 Java calls with an empty capture group as
unset or the reverse. vscode-textmate skips zero-length captures, so those
calls count as equal; no other engine needs this.

## Reproducing

```bash
./scripts/prepare-oniguruma-sources.sh
./scripts/prepare-onigmo-sources.sh
pnpm install --frozen-lockfile --dir benches/shiki_js
./scripts/compare-engines.py run /tmp/ferroni-compare --cases shared oniguruma micro textmate
./scripts/compare-engines.py report /tmp/ferroni-compare.md /tmp/ferroni-compare
```

Or dispatch the workflow:
`gh workflow run blacksmith-comparison.yml --ref main -f platform=both -f cases=all`.
The tables on this page come from
`./scripts/compare-engines.py tables benches/results/blacksmith-2026-10-09-37989957431 benches/results/blacksmith-2026-10-09-37999607702`,
the second run replacing the highlighting set of the first.

# Regex Benchmarks

How quickly can each engine validate text, extract captures, replace matches or
split graphemes? These comparisons use patterns and test inputs from real
projects, from simple expressions to complex patterns and advanced Oniguruma
features. Every engine has to return the required output before it is timed.

The results come from repeated Blacksmith measurements on ARM64/macOS and
x86-64/Linux. They measure isolated regex steps. Complete applications,
TextMate Scanner calls and Ferriki highlighting have separate boundaries.

## Inspect individual cases

Choose a platform, phase and comparator to inspect the work that matters to your
application. **Compile** measures preparing one pattern. **Compile + first use**
adds its first input. **Steady reuse** applies a prepared regex to the complete
input batch. These phases measure different amounts of work; their absolute
times cannot be compared as though each were one search.

The baseline is Ferroni's **standard public API**. Select **Ferroni error-aware
API** to compare the fallible `*_with` methods directly. Unsupported syntax,
different output and inconclusive timings remain visible in the tables.

<ProductionComparison />

Some compile and first-use measurements vary substantially between processes;
the displayed ranges include every run. Interval envelopes retain each process's
95% Criterion confidence interval. They are a descriptive screening aid, not a
cross-process significance test. Each platform used one VM,
so these results do not establish consistency across independent hosts. Host
power and thermal state were unavailable. This run did not measure memory.

## Comparable work before comparable speed

An engine must reproduce every fixture's defined output before timing: boolean,
first span, captures with unset groups preserved, all captures, replacement string
or grapheme chunks. Missing syntax, semantic differences, execution errors and
timeouts have separate statuses. A missing result is not a slow timing or a
negative match.

Patterns share one documented dialect recipe. Python strict-end anchors,
ECMAScript ASCII digits and PHP ASCII word classes are explicit. Match-at-offset
preserves the complete subject when lookbehind needs preceding context. Future
alternative solutions to the same task need their own profile and must include
necessary preprocessing and output work.

The Ferroni baseline uses the standard public `Regex` methods, including
`is_match`, `find_at`, `captures_at` and `captures_iter`. A separate **Ferroni
error-aware API** profile uses the fallible `*_with` searches and iteration with
`SearchOptions::new()`. Both use standard `replace_all` for replacement because
there is no fallible replacement API. Both profiles must pass the source oracles;
the baseline also receives a fallible preflight check to expose execution errors.

The two API paths currently manage match state differently: standard searches
can reuse the engine's cached workspace, while the parameterized searches create
fresh workspace. This can affect reuse costs even with empty search options.
Compilation uses the same builder in both profiles. The measured engine
implementation is unchanged; these rows expose the API cost separately.

The other comparators are C Oniguruma, pinned Ruby
Onigmo, PCRE2 interpreter/JIT, fancy-regex in Oniguruma mode with seek off/on,
and Rust regex. Construction includes each profile's contexts and selected JIT.
PCRE2's bundled source is pinned through the locked `pcre2-sys` dependency.
Both PCRE2 profiles enable UTF and UCP. Skipping repeated UTF-8 validation for
already-valid Rust strings does not disable Unicode character classes.
Replacement/output assembly stays within the operation boundary.

regexr 0.6.1 adds separate JIT-off and JIT-enabled profiles. Both use its default
SIMD feature and explicit `(?u)` Unicode mode. Its JIT-enabled selector may
retain a non-JIT backend; the selected backend is recorded. Native public Regex
methods, capture iteration and literal replacement are measured. Its public API
has no context-preserving offset search, so those cases report an API gap.
Fallible first-match/capture checks run before timing; native iteration and
replacement do not expose every execution error. Each regexr ratio uses the
Ferroni baseline from the same additional run.

## LLM regex pre-tokenization

The current [tiktoken patterns](https://github.com/openai/tiktoken/blob/4e71bbe0c078468e00fefbf94b39849389f346e5/tiktoken_ext/openai_public.py)
for `cl100k_base` and `o200k_base` add a separate application family, inspired
by regexr's tokenizer examples. Eleven shared upstream inputs per pattern cover
whitespace, contractions, numbers, multilingual text, emoji and the original
longer benchmark strings. Every complete match span is checked against Python
`regex` 2026.1.15 using the original expression.

The bounded possessive number quantifier in `cl100k_base` is written as an
equivalent atomic group for the Oniguruma-family dialect. Its other constructs
are preserved. Rejections and semantic differences remain visible; acceptance
of an older tokenizer example does not establish support for the current pattern.

These timings measure regex pre-tokenization, excluding BPE merges, vocabulary
lookups, special tokens and complete tokenizer throughput. They have their own
tables and aggregate and do not change the earlier 21-task aggregate.

<TokenizerComparison />

Eligibility describes these configurations. Rust regex, for example, disables
octal escapes by default and offers `RegexBuilder::octal(true)`; its rejection
of Django's email local-part expression in this profile is a dialect-option
difference. Other configurations or task-equivalent expressions need separate,
named profiles with the same checked output contract.

A different result is not necessarily a missing feature or a library defect.
For example, regexr joins an Indic consonant cluster that the retained Symfony
grapheme oracle separates. Its implementation includes the Unicode
[GB9c grapheme rule](https://www.unicode.org/reports/tr29/#GB9c).
The feature matrix still shows grapheme support; the workload requires the
specific retained output, so that result cannot enter its timing comparison.

## Measurement and interpretation

Compile, compile-plus-first-use and steady reuse are separate lanes. First use
concerns the first fixture, while steady reuse executes the complete fixture
batch. These are fresh-pattern costs in a warmed process; they do not measure
OS-process startup. Memory, where selected, is whole-process peak RSS including
runtime, catalog, allocator and output, rather than isolated pattern storage.

The runner starts with three independent processes per pair, 30 Criterion
samples per lane and three seconds measurement. It rotates/reverses engine order,
keeps raw samples and intervals, and reports inconsistent differences as
inconclusive. Short diagnostic runs cannot establish publication claims. Review
host conditions and stability before interpreting a publication candidate.

Each comparison lists its exact common tasks. Families carry equal aggregate
weight regardless of fixture or variant count. Aggregates with different supported
task pools do not establish an engine ranking. ARM and x86 results are reported
separately.

The aggregate takes the geometric mean of the median case ratios within each
family, then the geometric mean across families. It describes this selected
corpus rather than a production traffic mix.

The [corpus guide](https://github.com/sebastian-software/ferroni/blob/main/benches/regex_corpus.md)
contains runnable commands, case selection, measured
boundaries, current coverage limits and the requirements for adding cases.
